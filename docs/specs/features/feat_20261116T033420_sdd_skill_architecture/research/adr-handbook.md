# ADR `ai_engineering_handbook`: что берём, что не берём

| ADR | Что берём | Что не переносим |
|---|---|---|
| 26024 Structured commit bodies | Живой пример: LLM-генерация релизных заметок заменена парсером из структурированных тел — модель пишет «почему» один раз, машина форматирует | Собственный формат тела и его парсер: у нас другая норма о сообщении, перенос формата — M6 |
| 26045 Code as primary documentation | Формулировку границы: «enforce structure, not semantic quality»; «the linter prevents absence; review prevents vacuity» | Докстринги как единственный слой документации: проработка и спека прозой кода не заменяются |
| 26011 (superseded) | Улику: проверка наличия обещала «Zero-Drift Documentation»; сам ADR назвал исход — файлы ради гейта | Отношение 1:1:1 скрипт:тест:док |
| 26009 Ansible | Идемпотентность как свойство, проверяемое повтором; «check vs fix» как два режима одной вещи | Конкретный инструмент: принцип выжил, инструмент может смениться |
| 26003 (rejected) | «Решение, которое может принять только машина, принимает машина» — копировать принцип, а не `gitlint` | Отклонённый инструмент и его конфигурацию |
| 26040 Podman kube YAML | Артефакт — декларативный манифест, оркестратор — отдельная забота, манифест ревьюится | Именование сервисов и устройство `systemd`-юнитов |
| 26056 Blueprint validation | Шаблон проверяется, даже если его не меняли: иначе каждый новый файл рождается несоответствующим | Реестр `.vadocs/conf.json` |
| 26037 SVA C1/C4/C5 | C1: шаг без интерактивного входа; C4: у компонента есть цена; C5: не дублировать существующую проверку | Штрафную таблицу WRC |
| 26027 Model taxonomy | Выбор по задаче: разбор — reasoning-ось, исполнение по шаблону — agentic-ось | Привязку к фазам `aidx`/`aider` |
| 26012 Validation engine | Проверки как пакет с CLI и конфигом из `pyproject.toml` | Вынос в отдельный pip-пакет: для одного репозитория цена без потребителя |
| 26057 Skillopt | Требование доказывать пользу нормы на отложенной выборке | Сам механизм: стенда нет, и его цена — причина, по которой ADR остался proposed |

Ответ: ADR помогают не как схема, а как **замеры одного
и того же вопроса**, сделанные до нас. Переносить можно диагноз и формулировки
границы; нельзя — пространство имён, форматы и скрипты (M6). Два ADR полезны
как отрицательный результат: 26011 показывает, чем кончается проверка наличия,
обещавшая синхронность; 26057 — что эмпирика нормы верна и недоступна по цене.

## Что это меняет в границе и принципах

1. **Ярус 0 расщепляется на гейт и замер.** Гейт блокирует; замер печатает
   число и не блокирует. Смешение — путь handbook: замер, ставший гейтом,
   начинают обходить, а гейт, ставший замером, перестаёт замечаться.
2. **У яруса появляется третий признак — чем проверка доказана.** Фикстура, на
   которой проверка падает. Без неё строка «что ловит» — обещание.
3. **Принцип 4 расширяется на проверки:** у проверки, как у правила, есть
   владелец и срок; проверка без фикстуры — не проверка.
4. **Норма «каждый слой пишет, что не ловит» получает форму столбца.** В
   таблице он обязателен для каждой строки, иначе остаток не имеет адреса.
5. **«Один SDD-скилл» не меняется:** граница проходит внутри скилла, между его
   шагами, а не между скиллами.
