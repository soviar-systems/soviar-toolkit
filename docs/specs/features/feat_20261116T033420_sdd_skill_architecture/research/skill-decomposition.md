# Декомпозиция скиллов: контекст и изменение

Вопрос: держать один скилл `context-management` или разделить его на скилл
конституции и скилл изменения? Изменений сейчас только фичи, дальше будут и
другие. Решения нет; ниже — наблюдения, гипотеза и доводы обеих сторон.

## Наблюдения

1. `roadmap.md` уже планирует три скилла: **constitution**, **feature**,
   **validation**. Значит вопрос не гипотетический: текущий `context-management`
   держит нормы и для конституции, и для задач сразу, а milestone разводит их по
   роли.
2. Из четырёх файлов норм `context-management` три общие для любого проекта и
   любой работы: `criteria.md` (как судить), `layout.md` (где что лежит),
   `GLOSSARY.md` (слова). Только `research-package.md` — про пакет задачи, то
   есть про изменение.
3. Изменения заводят только фичей: путь `docs/specs/features/<feat>/`. Что
   дальше будут другие виды изменений, уже записано в `GLOSSARY.md`; имя
   `features` в пути — временное.
4. Признак, по которому режется скилл, нигде не назван. Возможные оси: по
   предмету (конституция / изменение), по стадии (написание / валидация), по
   читателю (автор / гейт).
5. `context-guard` берёт нормы по разделу «Пакет» в `SKILL.md` и не перечисляет
   файлы сам. Разделение контракт не сломает, если владелец назовёт нормы в том
   же разделе.

## Гипотеза

Работу с контекстом делят на два скилла: скилл конституции — как писать и
проверять фундаментальные документы проекта; скилл изменения — как заводить и
вести пакет одного изменения. Общие нормы (критерии, раскладка, слова) при этом
остаются там, где их читают оба.

## Доводы за разделение

1. Читатели и моменты разные: конституцию правят редко и по завершении работы,
   пакет изменения — каждый день. Один скилл заставляет обоих читать про чужое.
2. Срок жизни разный: конституция переживает задачи, пакет изменения умирает
   вместе с задачей. Общий скилл мешает зафиксировать эту разницу нормой.
3. `roadmap.md` уже называет `constitution` отдельным скиллом — разделение
   приводит раскладку скиллов в соответствие с планом, а не создаёт новый план.
4. Пакет изменения будет расти: сейчас в нём проработка, дальше требования, план,
   трассировка, журнал решений — семь открытых вопросов `roadmap.md`. Держать это
   в скилле, который отвечает ещё и за конституцию, — та же простыня, от которой
   уже пришлось разрезать `layout.md`.

## Доводы за единство

1. Критерии, раскладка и глоссарий общие. При двух скиллах их либо дублируют,
   либо выносят в третий дом — и тогда скиллов не два, а три, и непонятно, кто
   из них владелец.
2. Проверка одна: `context-guard` судит и конституцию, и пакет изменения по одним
   критериям. Разделив нормы, придётся либо оставить гейт вне обоих скиллов, либо
   завести ему два входа.
3. `context-management` уже устроен по виду знания, а не по предмету: процесс,
   критерии, места, слова, состав пакета. Деление по предмету режет поперёк этого
   устройства.
4. Скилл — единица загрузки, а не единица темы. Пока оба читателя открывают одни
   и те же нормы, разделение добавляет переход, а не экономит контекст.

## Что уже проверено на себе

Разрез по виду знания сработал: устройство `README.md` вынесли из `layout.md` в
`research-package.md`, и оба файла стали читаемыми — `layout.md` вернулся с 112
строк к 41. Это довод в пользу того, что резать надо по виду знания, а не по
предмету; но он же показывает, что разделение возможно без второго скилла.

## Блокеры

Задачу `1#issue-63` не закрывать, пока не решено:

- один скилл контекста или два — конституция и изменение;
- по какому признаку режется: предмет, стадия или читатель;
- кому принадлежат общие нормы — критерии, раскладка, глоссарий — при любом
  ответе;
- остаётся ли `context-guard` один на оба предмета или получает два входа;
- переименовывается ли `docs/specs/features/` в общий дом изменения, раз фичи не
  единственный его вид.
