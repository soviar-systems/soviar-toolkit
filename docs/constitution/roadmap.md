## Сейчас — конфигурация Qwen Code CLI

Спецификация: `docs/specs/features/feat_20261114T192255_qwen_code_cli_config/`
Ветка: `feat/3#issue-65-qwen-code-cli-config-wt` (задача 65 проекта 3)

Состав:

- `bootstrap.py` в корне — точка входа с флагами по инструментам, реестр, коды
  выхода, идемпотентность
- `tools/qwen_code_cli/` — установщик, слияние настроек, хук `PreToolUse`,
  MCP-сервер поиска Ollama
- `tools/qwen_code_cli/payload/` — артефакты: `settings.json`,
  `statusline-command.sh`, хук, MCP-сервер
- тесты на всё перечисленное
- `skills/context-management/` — раскладка носителей контекста и критерии, по
  которым их проверяют
- `skills/context-guard/` — выверка консистентности контекста перед коммитом

Два уровня тестов. Первый — юнит: кормит скрипт данными и проверяет вывод.
Второй — проверка артефактов: `payload/settings.json` парсится, каждая команда
в `hooks` указывает на существующий файл, абсолютных домашних путей нет. И один
smoke-тест, запускающий настоящий `qwen` в headless с подстановкой команды:
только он отвечает на вопрос «принял ли хост наш хук».
Общее правило про уровни тестов сюда не пишем — это практика команды.

## Milestone: базовые скиллы для полноценной агентной разработки

Закрывает переход от «агент помогает» к «агентная разработка как процесс».

### 1. SDD (по черновику `misc/sdd-from-deeplearning_ai.md`)

- **constitution** — написание конституции и её валидация: пропущенные вопросы,
  несоответствия между носителями контекста
- **feature** — разработка спецификации фичи: требования, план, декомпозиция на
  задачи. Сюда же входят правила планирования (размер итерации, критерии
  закрытия фазы, обязательность спецификации до кода)
- **validation** — проверка реализации на соответствие спецификации и
  конституции

### 2. pre-commit review — та же валидация, но на изменениях

Скилл уже существует (`skills/pre-commit-review/`), нужно довести до двух
режимов:

- **light** — один ревьюер + один закрывающий + шаблон коммита
- **heavy** — три ревьюера + два проверяльщика + один закрывающий + шаблон
  коммита

Предмет проверки — коммит, а не индекс. Сейчас и `pre-commit-review`, и
`context-guard` судят индекс; правки ревьюера меняют тот же индекс, поэтому
неудачное ревью портит работу, которую проверяло, и страховки, что мы ничего не
испортили, нет. Порядок обратный: сначала коммит готовой работы, затем дифф этого
коммита против его базы, и сверяется этот дифф — закоммиченное ревьюер не
изменит. Побочный выигрыш: правило улики из раздела 3 становится выполнимым —
отчёт приходит коммитом поверх проверенного, и проверенный в его шапке и есть
`HEAD`. Сейчас правило и порядок противоречат друг другу: правило требует
`HEAD`, а при одном коммите в CI `HEAD` уже указывает на сам коммит с работой.
Следствия для стража: гейт перестаёт быть `--cached`, формулировка «проверка идёт
по индексу» отменяется, отчёт приходит вторым коммитом, а проверка в CI сравнивает
шапку с родителем того коммита, в котором лежит отчёт.

Базу диффа задают явными `sha1..sha2` из шапки отчёта, а не `HEAD~1`: у
merge-коммита родителей два, `HEAD~1` берёт одного из них, и дифф покажет не то,
что проверяли.

Значит шапка отчёта меняется: вместо одного поля «Родительский коммит» — два,
`База` и `Вершина`. Пока поле одно, `HEAD` снова просочится в гейт: пару нельзя
вывести из текущего состояния репозитория, её надо назвать.

Отчёты — в `docs/review/`, формат вердикта — в скилле `context-guard`.

### 3. Страж контекста на коммите

Локальный хук ловит забывчивость, но `--no-verify` его обходит, а запись об этом
в истории ничего не исправляет. Поэтому слоёв три, и последний обойти нельзя:

- `.githooks/pre-commit` — отказ на коммите; `core.hooksPath` ставит
  `bootstrap.py`, логика — `tools/context_guard/` с юнит-тестами на разбор путей
- хук агента (`PreToolUse`, как `block_command_substitution.py`) — команда
  `git commit --no-verify` не выполняется
- CI/CD — те же проверки на стороне сервера; локальный обход не проходит тихо, а
  ломает сборку

Набор и улика одинаковы на всех слоях:

- набор: `docs/**` кроме `docs/review/`, `AGENTS.md`, `GLOSSARY.md`, `README.md`,
  `skills/**`
- улика вместо обещания: в индексе есть `docs/review/implemented/review_*.md`, и
  поле `Вершина` в его шапке называет проверенный коммит — на слое хука это
  `git rev-parse HEAD`, в CI это родитель коммита с отчётом
- отчёт без находок — законный проход

Почему git-хук, а не хук агента: правило про коммиты, а не про qwen. `PreToolUse`
действует в одном хосте и видит строку команды вместо индекса.

### 4. backlog

Отдельный каталог в отдельном worktree, где каждый todo — отдельный файл с
временнóй меткой в имени.

- закрывается коммитом, затем удалением файла отдельным коммитом — то есть
  хранится только в git
- ветка **никогда** не вливается в `master`, но регулярно ребейзится на него,
  чтобы оставаться актуальной
- общая ветка для всех агентов: быстро доставлять todo, не дожидаясь PR в
  `master`

### 5. agents-md

Первичное написание и дальнейшая поддержка `AGENTS.md`:

- убирать no-op формулировки
- только actionable инструкции
- файл — входная точка и индекс носителей контекста, а не подробный README
  проекта

## Отложено

Названное здесь — предстоящая работа без порядка и срока, а не отказ: названный
путь, которого в дереве нет, отсутствует намеренно, и находкой это не считается.
Порядок и срок появятся, когда пункт переедет в раздел текущей работы.

- Протокол подключения агентов (ACP) — не решено, как `pi` получает
  спецификации; см. «Разделение ролей агентов».
- Gherkin для спецификаций — открытый вопрос, нужен ли он вообще.
- Политика когнитивной нагрузки — как измерять «обозримость» изменения.
- Триггер стража: сейчас это коммит с носителем контекста, а дрифт создают
  коммиты кода — носитель контекста описывает дерево, код его меняет. Нужен
  запуск на коммитах кода.
- Механическая сверка с деревом: критерий 4 пока проверяется вручную, по паре
  «носитель контекста ↔ этот roadmap». Скрипт должен брать пути из указателей и
  прозы, но не из блоков-образцов: в `tech-stack.md` блок раскладки модуля —
  норма, и проверка существования на нём даст ложные находки.
- Архитектурные решения отдельным домом: сейчас они живут в спеке задачи и
  умирают вместе с ней, а отменённое решение некуда перевести в статус
  «отменено».
- Глоссарий: «milestone», «фаза», «состав» — три имени одного деления работы.
- Владелец и дата пересмотра у `mission.md` и `roadmap.md`: сейчас оба
  обновляются по памяти.
- Отслеживание «сделано» в roadmap: нет ни раздела, ни маркера, поэтому
  «сделано» в нём неотличимо от намерения. Нужен маркер, чтобы работа
  закрывалась не памятью.
- Жизненный цикл спецификации: архив в `docs/specs/implemented/` при закрытии
  задачи, иначе цена прогона растёт с историей, а не с коммитом.
- Индекс отчётов `docs/review/INDEX.md`: через год вход в историю потерян, имена
  по времени ничего не говорят.
- Трассировка требований: `R1..Rn` в спецификации, ссылки из плана и тестов.
- `misc/**` в наборе проверки шлюза, иначе «файл вне раскладки — дефект» к нему
  не применяется никогда.
- Скиллы установлены симлинками из worktree: при его удалении они перестают
  работать молча. Ставить из канонического клона.
- Шаблоны спецификации и плана: обе спеки написаны с нуля, легенда
  `[x]/[ ]/[-]/[?]/[!]` изобретена внутри плана. Второй проект изобретёт свою.
- Журнал решений со статусом: D-номера уже есть, у отменённого решения нет
  места, куда переехать, — оно остаётся в спеке как история.
- Связь спеки, задачи и ветки одним полем в шапке: сейчас только прозой.
- Признак «готово» и артефакт закрытия задачи: сейчас это `[x]`, поставленный
  тем, кто делал.
- Владелец и триггер пересмотра самих критериев и раскладки: условия вида
  «три `drop` подряд — пересмотреть критерий», а не дата в календаре.
- Общекомандные правила, осевшие в конституции одного проекта: правила тестов в
  `docs/testing.md`, запрет секретов в `mission.md`. Переносить в скиллы.
- Подготовка контекста к задаче: спека — результат аналитической работы, а сама
  работа — гипотезы, разбор источников, ход рассуждений — живёт только в сессии и
  теряется. Нужно решить, где она ведётся и что из неё переживает сессию:
  сравнить личный `ai_engineering_handbook` (`misc/plan`) с внешними OpenSpec,
  superpowers и GitHub Spec Kit.
